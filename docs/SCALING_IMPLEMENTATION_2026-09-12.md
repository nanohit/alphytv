Миграционный скрипт читает старое хранилище только для переноса существующих данных.

## Общий кэш: границы и стоимость

- Публичные объекты распределены по трём организациям: `xoathqkggcuyoyutxwri`, `hcuhanruaclhiltpdegc`, `matozzgmaranfemgxpzy`. Две копии каждого объекта. Фиксированное распределение 256 групп не зависит от добавления четвёртого host.
- Слоты свежести: film ≤7 суток, staff/similars ≤30 суток, keyword search ≤6 ч. Сроки сдвинуты по группам, чтобы весь каталог не истекал одновременно.
- Подтверждённое отсутствие хранится 6 ч в состоянии и gateway, но не занимает неизменяемый месячный URL. Ошибки/таймауты не превращаются в «тайтла нет» или пустое «Похожее».
- Deno объединяет одинаковые запросы в пределах instance. Ограничения: 32 разных холодных объекта одновременно, 512 memory entries, примерно 16 MiB JSON-данных плюс накладные расходы runtime. Это не лимит всей памяти Deno.
- SQL lease объединяет upstream-fill между instances, но каждый новый instance может вызвать broker. Тест одного instance нельзя выдавать за измерение глобального fan-out.
- Каждый KU ключ резервируется атомарно, до 480 запросов за московские сутки. Дополнительные ключи увеличивают доступное число **новых/обновлённых объектов**, а не ёмкость Supabase или Deno.
- Prewarm: не более 120 fill-attempts/run, seed film/staff/similars и film-метаданные одного шага реального внешнего графа. Без персональных историй пользователей. В худшем случае 24 полных запуска — 2880 попыток за сутки; это верхняя граница, прогретые файлы читаются без KU.
- Ежедневная очистка оставляет текущий и предыдущий v2 слот. Удаление файлов идёт через Storage API, а не DELETE из `storage.objects`. SQL очищает старые query/pending записи и историю квот старше 30 дней. v1 файлы сохранены для перехода/отката.
- Новые аккаунты не используются автоматически: перенос групп, функций и квот должен быть явным. Центральное состояние broker остаётся в одной организации.

Расчёт после выкладки вести отдельно: `DAU × 30 × Function calls / активный день` и `DAU × 30 × cached/uncached bytes / активный день`, распределённые по фактическим организациям. DAU без числа поисков, открытий, серий и доли холодных тайтлов не является достаточной нагрузочной моделью.

## Порядок выпуска

1. Выполнено: получены и проверены `ALPHY_KEY_POOL_MASTER_KEY` и Deno auth. `.env.scaling` уже содержит приватную подготовленную конфигурацию; файл исключён Git. Не использовать masked значения из `vercel env pull`.
2. Повторить `scripts/migrate-admin-store.mjs` с `ALPHY_STATE_URL`, `ALPHY_STATE_SERVICE_KEY`, master key и URL старых catalog, catalog pointer и encrypted pool. Скрипт следует versioned pointer, проверяет revision, расшифровку и JSON roundtrip. Перед переключением повторить перенос: админ мог изменить каталог со времени первого копирования.
3. Настроить Vercel Production/Preview: `ALPHY_STATE_URL`, `ALPHY_STATE_SERVICE_KEY`, прежний настоящий `ALPHY_KEY_POOL_MASTER_KEY`; сохранить существующие admin credentials. Переменные применяются к новой deployment, сами по себе сайт не переключают.
4. Применить `supabase/functions/titles/schema.sql`, выкатить titles. Применить broker/schema и `supabase/kp-maintenance.sql` через `scripts/deploy-kp-broker.mjs`, передав management-token map, `KP_BROKER_TOKEN`, private runtime token и KU bootstrap keys. `kp_complete_v2` отделён от legacy completion, чтобы старый worker не пометил v1-файл как v2.
5. Выкатить Deno с прежними настройками приложения плюс `KP_BROKER_TOKEN`, `ALPHY_CACHE_URL`, `ALPHY_CACHE_SERVICE_KEY`. Проверить cold/hit `/kp`, KU ошибки и fallback. Секрет runtime-пула остаётся прежним; не генерировать новый вместо существующего без согласованной ротации.
6. Выкатить Lift `/info` cache change на все четыре Lift relay-проекта. Подготовить GitHub secrets `KP_BROKER_TOKEN` и `KP_STORAGE_KEYS` (service keys только трёх metadata hosts). Проверить authenticated prewarm и maintenance `--dry-run`.
7. Сначала опубликовать commit с ассетами в GitHub и прогреть его jsDelivr URL; затем строить/выкатывать Vercel shell, ссылающийся именно на этот commit. Локальная сборка с ещё не опубликованным SHA не является рабочей CDN-выкладкой.
8. После нового `/api/catalog-snapshot` активировать изменённые workflows, вручную проверить sync → fallback build → search publication и baked Letterboxd. Убедиться, что новый клиент не вызывает `/api/client-key-pool`, PoiskKino metadata batch или публичный KP broker напрямую.

## Что ещё мешает обещать выполнение всех критериев

1. Нужен реальный разрешённый источник новых Collaps/Zona inventory/delta. Текущий код добавляет эти плееры к уже известным KP-тайтлам; он не обнаруживает весь новый каталог каждого провайдера.
2. Строгий срок ≤6 ч требует надёжного планировщика и наблюдения за возрастом очереди. В проверенных GitHub runs интервал достигал 2–3 ч, несмотря на hourly cron. Новый checkpoint и `workflow_run` убирают логические пропуски и лишнее ожидание публикации, но не обеспечивают SLA scheduler.
3. Остались ограничения полного CDN outage, горячего shard/организации, единого mzona IP и Deno memory-time. Дополнительный Supabase аккаунт сам по себе их не устраняет.
4. Нужен короткий живой нагрузочный прогон разных действий и сверка Usage по организациям/Deno. Без этого 5–10k DAU на Free — цель, а не установленный результат.
